## 1. 业务边界优先

先画业务责任边界，再画技术组件。一个生产级智能体至少包含：

- 模型：在不完备信息下理解、判断、规划或生成；
- 工具：获取事实或改变外部世界；
- 编排：管理循环、状态、预算、策略与终止；
- 运行服务：身份、会话、记忆、部署、观测、评测和治理。

不要把所有组件都塞进一个 Agent。业务规则和事务边界应由确定性系统持有，Agent 只获得完成职责所需的最小视图与动作。

## 2. 自治级别

使用最低可行自治：

| 级别 | 适用场景 | 主要新增风险 | 必需控制 |
| --- | --- | --- | --- |
| 模型能力 | 摘要、分类、抽取、草拟 | 幻觉、格式漂移 | Schema、事实来源、人工抽检 |
| 工具增强 | 查询事实、执行单一动作 | 错工具、错参数、越权 | 工具契约、授权、结果校验 |
| 策略型 Agent | 动态多步问题、路径不能预先穷举 | 循环、成本、错误累积 | 预算、终止、轨迹评测、补偿 |
| 多智能体 | 权限/上下文/专业能力需隔离 | 协调失败、死锁、责任模糊 | 角色契约、共享状态规则、全链路 Trace |
| 自演化 | 可离线验证且验证远易于生成 | 奖励投机、能力漂移 | 沙箱、离线评测、人工批准、可回滚发布 |

“能做”不等于“应当做”。级别越高，需要的证据、治理和运营成熟度越高。

## 3. 确定性与生成式能力分工

适合模型：

- 意图与语义理解；
- 开放式信息综合；
- 动态计划候选；
- 语言和多模态内容生成；
- 无法穷举规则的模糊判断。

适合普通代码或 Workflow：

- 身份与权限校验；
- 精确计算、Schema 验证和格式转换；
- 事务、状态机、幂等、重试与补偿；
- 金额、配额、删除、发送和生产变更；
- 可以明确表达的固定路由和合规规则。

推荐结构是确定性骨架包围模型节点：输入校验 → 模型判断 → 策略检查 → 工具执行 → 结果验证 → 状态提交。

## 4. 单智能体与多智能体

默认单智能体。只有满足至少一个强理由并能独立验收时拆分：

- 不同角色需要隔离权限或敏感上下文；
- 子任务需要不同工具、模型或 SLA；
- 子结果有稳定、版本化的输入输出契约；
- 子角色可以独立评测与替换；
- 任务可真正并行，或必须有独立批评/审批者；
- 单体的工具集合和 Instructions 已导致选择质量下降。

不要因以下理由拆分：名字听起来像团队、流程步骤多、想展示自治、一个长 Prompt 看起来不优雅。

拆分后必须定义：责任归属、委派输入、返回 Schema、超时、取消、重试、幂等、共享状态、部分失败、聚合规则和 Trace 传播。

## 5. 编排模式

- 顺序：步骤稳定、前一步输出是后一步输入；优先用确定性 Workflow。
- 协调者/路由：请求类型动态，专家边界清晰；路由本身需要评测。
- 并行汇聚：子任务独立且延迟重要；必须处理部分结果和超时。
- 生成-批评/迭代改进：质量标准可明确表达，收益覆盖额外成本；设置最大轮次与停止规则。
- Human-in-the-Loop：风险、歧义或责任不能交给模型；保留可恢复状态和清晰批准界面。
- Agent-as-a-Tool：调用方需保留会话控制，只消费一个边界清晰的子结果。
- A2A：跨团队、跨运行时、长任务和正式服务契约；不用于紧耦合本地函数替代。

## 6. 模型与运行时

不要按通用榜单选模型。用业务评测集比较：任务成功、工具调用可靠性、延迟、成本、安全和稳定性。

模型路由要有可解释规则。复杂规划可用能力更强的模型，分类、抽取和摘要可用更快更便宜的模型，但每条路由都要单独及端到端评测。

运行时至少支持：显式状态、可中断与恢复、预算/超时、工具策略钩子、结构化 Trace、版本标识和可替换模型。框架抽象应避免业务契约直接绑定内部 Session/Event 类型。

## 7. 互操作边界

- MCP 面向工具和资源：结构化、相对原子、明确输入输出。
- A2A 面向智能体：任务导向、可多轮、可异步、包含自主规划。
- 内部函数优于协议：同一进程、同一团队、稳定紧耦合能力无需为“标准化”额外网络化。
- 注册中心按规模引入：当发现、复用、审计或访问治理成为瓶颈时再建设。

## 8. 设计审查问题

- 为什么这里必须由模型判断？
- 最低自治方案是什么，为什么不够？
- 哪个组件拥有业务事实与最终提交权？
- 每个 Agent 是否能用一句话描述唯一责任？
- 多智能体是否降低了总体复杂度，而非转移复杂度？
- 部分失败、重放、超时和取消时会发生什么？
- 模型、工具或框架替换是否会破坏业务契约？
- 系统如何知道任务已完成、应拒绝或应停止？
