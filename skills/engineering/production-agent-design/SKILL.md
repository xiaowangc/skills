# 生产级智能体设计

## 目标

把业务目标转换为可验证、可治理、可运营的智能体系统设计。优先给出贴合当前业务约束的最小充分方案，不为追求“智能体化”而引入自治、记忆、多智能体或开放工具协议。

## 核心立场

- 把智能体视为“模型、工具、编排、状态与运行服务组成的自治软件系统”，而不是 Prompt。
- 先证明业务任务需要模型判断；权限、校验、计算、状态流转、审批、幂等、重试和补偿优先使用确定性代码或 Workflow。
- 从最低可行自治级别和单智能体开始；只有边界、权限、上下文或独立评测要求成立时才拆分多智能体。
- 把安全、评测和可观测性作为架构输入，不作为上线前补丁。
- 以真实业务结果判定“好”，再用轨迹、组件和系统指标定位“为什么”。
- 把生产失败转成永久回归样本，形成 Observe → Act → Evolve 闭环。

## 工作流程

### 1. 建立事实基线

先读取用户提供的 PRD、流程、现有代码/Agent 资产、接口契约、数据策略和运行约束。明确区分：

- 已确认事实；
- 合理假设；
- 仍需业务、合规或技术负责人决定的问题。

当信息不足时，先给出带假设的可执行初稿，只询问会实质改变架构或风险边界的问题。

完成标准：业务参与者、触发方式、期望结果、失败影响、数据来源、外部动作和人工责任均已明确或显式标记未知。

### 2. 判断是否应该使用智能体

按顺序判断：

1. 任务是否需要语言理解、开放分析、动态规划或不完备信息下的判断？
2. 固定规则、搜索、普通服务或 Workflow 是否能以更低风险完成？
3. 智能体带来的收益是否覆盖非确定性、延迟、成本和治理负担？

若答案是否定，明确建议非智能体方案。若仅部分步骤需要判断，设计“确定性骨架 + 模型判断节点”的混合系统。

### 3. 定义业务任务契约

把“做一个某某智能体”收敛为以下可验证内容：

- 使命与不做什么；
- 目标用户、业务所有者和风险所有者；
- 输入、输出及结构化契约；
- 成功、部分成功、失败和拒绝的定义；
- 业务 KPI 与质量门槛；
- 时间、成本、轮次和资源预算；
- 人工接管、审批与申诉路径。

需要完整模板时读取 [design-deliverables.md](references/design-deliverables.md)。

### 4. 选择自治级别与系统边界

从最低级别起选择：

- 模型能力：单次理解或生成，无外部动作；
- 工具增强：读取事实或执行边界明确的动作；
- 策略型智能体：动态拆解多步任务并管理上下文；
- 多智能体：多个可独立负责、授权、评测的角色协作；
- 自演化：仅在离线、受控、可回滚且有强评测与审批时考虑。

选择单/多智能体、编排模式或互操作方式时，读取 [architecture-and-orchestration.md](references/architecture-and-orchestration.md)。不得仅因流程步骤多就拆成多智能体。

### 5. 设计工具、权限与行动控制

对每项能力确定它是知识、工具、Workflow 还是另一个 Agent。为每个工具定义：用户任务语义、输入/输出 Schema、权限主体、数据分类、副作用、幂等性、超时、重试、错误语义、审计字段和审批条件。

涉及 Function Tool、MCP、A2A、外部 API、文件/浏览器/代码执行或不可逆操作时，必须读取 [tools-interoperability-security.md](references/tools-interoperability-security.md)。把工具注解视为提示而非安全保证；在模型外执行授权和策略。

### 6. 设计上下文、会话与记忆

建立上下文预算，说明每类信息为何进入本轮模型上下文、由谁提供、可信度如何、何时过期、如何压缩。严格区分：

- Session：原始会话事件和当前工作状态；
- Memory：跨会话提取、合并并可检索的知识；
- RAG：共享、相对静态、权威的外部事实；
- Artifact：不宜直接塞入上下文的大对象。

涉及长对话、个性化、长期状态、多智能体共享知识或自适应时，必须读取 [context-session-memory.md](references/context-session-memory.md)。没有明确用途、生命周期、隔离和评测方案时，不增加长期记忆。

### 7. 以风险为中心设计安全

为数据流和每个动作标注风险等级，至少覆盖：身份、认证、授权、最小权限、租户隔离、凭证处理、Prompt/工具注入、数据泄露、记忆投毒、供应链、沙箱、审批、审计、撤销和应急停用。

把高风险写操作设计为“提议 → 策略校验 → 人工批准 → 执行 → 验证 → 审计”；设置工具级熔断器和降级路径。安全细则读取 [tools-interoperability-security.md](references/tools-interoperability-security.md)。

### 8. 设计质量证明

从外到内建立评测：

1. 业务结果与端到端任务成功；
2. 效果、效率、鲁棒性、安全四类质量指标；
3. 规划、工具选择、参数、工具结果解释、检索、记忆和多智能体通信的轨迹评测；
4. 确定性断言、领域规则、LLM/Agent Judge 和人工评审的组合；
5. 典型、边界、对抗、失败恢复和拒绝样本组成的版本化数据集。

设计评测、可观测性或上线门禁时，必须读取 [quality-evaluation-observability.md](references/quality-evaluation-observability.md)。不得只用“最终回答看起来不错”作为验收。

### 9. 设计生产生命周期

说明版本化对象、环境、CI/CD 门禁、灰度、回滚、运行预算、SLO、告警、人工值守、事件响应和持续改进机制。涉及部署、扩缩容、长期任务或上线评审时，读取 [production-agentops.md](references/production-agentops.md)。

至少要求代码、Instructions、模型配置、工具 Schema、策略、记忆 Schema 和评测数据可追溯到同一发布版本。

### 10. 输出决策而非概念堆砌

按 [design-deliverables.md](references/design-deliverables.md) 选择合适深度，至少输出：

- 结论与推荐方案；
- 业务任务契约；
- 系统边界和关键数据流；
- 关键设计决策及理由；
- 风险、控制与人工责任；
- 评测、上线门禁和运营闭环；
- 未决问题、假设与分阶段路线。

每个重要建议都写清楚“业务依据、采用条件、代价/风险、验证方式”。不要把特定云产品当成原则；产品名只可作为可替换实现示例。

## 生产就绪硬门槛

若以下任一项缺失，把结论标为“未达到生产就绪”，并列出补齐条件：

- 没有可测的任务成功定义或风险所有者；
- 外部写操作没有确定性授权、审批或审计；
- 输入输出、工具或 Agent 间没有版本化契约；
- 长期记忆没有范围隔离、来源、删除和投毒防护；
- 没有覆盖真实失败的评测集和发布阈值；
- 无法通过 Trace 还原模型、工具、状态和委派轨迹；
- 没有预算上限、超时、终止条件、降级或熔断；
- 没有灰度、回滚和生产事件反馈闭环。

## 证据与适用边界

本技能基于 Google 2026 年 5 月更新的五份智能体白皮书，并结合当前仓库对框架中立、类型化契约、最小权限、评测数据集和 `python main.py validate` 的约定重新组织。需要核对概念出处与覆盖范围时读取 [source-map.md](references/source-map.md)。白皮书中的产品能力和协议状态可能变化；做具体技术选型时再核对当前官方文档。
